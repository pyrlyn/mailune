# BoltFFI survey (B10)

Should Mailune move its bindings from UniFFI to BoltFFI? Short answer: **not now.** Keep UniFFI (`mailune-ffi`, B2) and the hand-written C ABI (`mailune-capi`, B6). Look again when one of the triggers at the end fires.

Every fact below was checked on 2026-10-08 against the source linked next to it.

## What is in the tree today

- `mailune-ffi` uses uniffi 0.32.2 in proc-macro mode. It has records, one error enum, an async export (`has_token`) and a foreign trait (`HostSecrets`). Swift and Kotlin are generated by uniffi-bindgen. C# comes from the pinned `uniffi-bindgen-cs` fork that ketch already uses (workspace `rust.md`).
- `mailune-capi` is a C ABI for the Vala shell. It sends JSON records in an envelope, and it has a cbindgen header, a VAPI and drift tests. It is hand-written because no UniFFI generator targets C or Vala.
- The calls are coarse. A shell folds a batch of events and gets one `ViewState` back, and a thread-list page is one call. Per-call overhead is not on the hot path. The performance budget in `docs/architecture.md` is for the store query (50 ms for a page at 100k messages), not for the FFI hop.

## Comparison for Mailune

| Concern | UniFFI (in the tree) | BoltFFI 0.31 |
| --- | --- | --- |
| Swift, Kotlin | Generated. ketch and cox ship this path. | Generated, with packaging included. |
| C# (WinUI 3) | Needs the pinned third-party `uniffi-bindgen-cs` fork. | Native target. **This is BoltFFI's strongest advantage for us.** |
| C / Vala (GTK4) | No generator. `mailune-capi` is hand-written. | Experimental, sync only, no closures. It would not replace `mailune-capi`, which is sync and JSON anyway. |
| WASM / web | Not a UniFFI target. The later web mode is planned on wasm-bindgen (`mailune-wasm`). | Full support. Worth looking at when the JMAP-direct WASM mode starts. |
| Async and callbacks | Async exports and foreign traits work today (B2). | Supported on managed targets, not on C. |
| Call overhead | A serialised buffer per call. Not a bottleneck for coarse calls. | Lower, by the vendor's numbers. That does not matter at our call rate. |
| Stability | 0.x, but stable in practice across ketch and cox. | 0.x with a breaking minor release about every two to four weeks (0.28 to 0.31 in ten weeks). Crux pins an exact version. |
| Cost of switching | None. | Rewrite the B2 derives, regenerate the B3/B4 packaging, retest. The forward-only syn test would need BoltFFI's `#[export]` added. |

## Decision

Do not switch. The cost is a rewrite of every binding and of the packaging scripts. What we would gain is call speed we do not need, plus a C# generator. The C# part matters, but the pinned fork already works in ketch. Its stability is also a risk: BoltFFI breaks its API every few weeks, and Crux itself pins an exact version and still keeps uniffi-bindgen next to it.

Keep `mailune-ffi` free of UniFFI types outside its own records, so a later switch stays a surface change: the contract and `mailune-app` carry no binding derives today.

## Triggers to look again

- BoltFFI reaches 1.0, or goes three months without a breaking minor release.
- The `uniffi-bindgen-cs` fork falls behind uniffi 0.32, or blocks the Windows shell (D-tasks).
- The JMAP-direct WASM web mode starts, and wasm-bindgen's object marshalling shows up in a profile.
- A profile shows FFI call overhead in a user-visible path, such as scrolling the thread list.
